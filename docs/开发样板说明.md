# 后端开发样板说明

## 参考模块

商品类别模块是标准 CRUD 样板：

- `Controllers/CategoriesController.cs`：路由、鉴权、HTTP 状态码和统一响应。
- `Services/ICategoryService.cs`：业务能力接口。
- `Services/CategoryService.cs`：数据库查询、业务校验和逻辑删除。
- `Dtos/CategoryDtos.cs`：请求与响应模型及参数校验。
- `Program.cs`：依赖注入与 Swagger 配置。

商品模块展示分页、关联查询、条码唯一校验、库存聚合和预警查询，可作为复杂查询样板。

## 新功能实现顺序

1. 在 Apifox 定义 URL、HTTP 方法、参数、响应结构和错误状态。
2. 从 `dev` 创建个人功能分支，禁止直接在集成分支开发。
3. 创建请求 DTO 和响应 DTO，不直接暴露 EF 实体。
4. 定义 Service 接口，在 Service 中实现业务规则和数据库访问。
5. 创建 Controller，仅负责协议转换、鉴权和响应封装。
6. 在 `Program.cs` 注册 Service，并确认 Swagger 契约与 Apifox 一致。
7. 执行本地构建、格式检查、Swagger 自测和真实数据库回归。
8. 与前端完成小联调，再发起合并请求等待评审。

## 代码约定

- Controller 路由统一使用小写复数资源名，**不加 `/api` 前缀**。
- 业务接口使用 `[Authorize]`；公开接口显式使用 `[AllowAnonymous]`。
- 所有响应使用 `ApiResponse<T>`；分页响应使用 `PageResult<T>`。
- 查询尽量使用 `AsNoTracking()`，筛选、排序和分页必须在数据库端完成。
- 输入长度、状态值、唯一性和外键存在性在 Service 中校验。
- 删除优先采用业务约定的逻辑删除，禁止无确认的物理删除。
- 数据库结构和 API 契约已冻结；确需变更时先说明原因和影响，再同步脚本与 Apifox。

## 完成标准（DoD）

- [ ] Apifox 契约已确认，字段类型和必填项明确。
- [ ] Controller、Service、DTO 分层完整并已注册依赖注入。
- [ ] 成功、参数错误、未授权、不存在和业务冲突场景均已验证。
- [ ] `dotnet format --verify-no-changes` 通过。
- [ ] `dotnet build --no-restore` 通过且无警告。
- [ ] Swagger/OpenAPI 已更新，并与 Apifox 保持一致。
- [ ] 涉及数据库变化时，脚本已更新并在 Oracle 上验证。
- [ ] 前后端小联调通过。
- [ ] 合并请求已通过代码评审，方可合入 `dev`。
